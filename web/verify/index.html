Check every claim yourself

Every number Talyx shows can be rebuilt from public RPCs. These are the addresses, keys, encodings and commands to do it.

Testnet only and unaudited. Talyx trusts V3’s two BEEFY keys, which are probably development keys, and V3’s sudo key. It trusts no relayer and no committee.

Three checks on real V3 data

  1. The BEEFY keyset

    keccak256(keccak256(key 1) ++ keccak256(key 2)) equals MmrLeaf.BeefyAuthorities, 0xc745…a7d5.

  2. Both signatures on block 279,494

    Recovering the two signatures over keccak256(commitment) gives the two BEEFY keys, in order.

  3. The MMR root at block 279,493

    Bagging the 8 on-chain peaks right to left reproduces mmr_root, 0x073b…93a1.

Runs in this browser with viem. Nothing is sent anywhere.

The claim

A filler cannot be paid unless V3’s BEEFY keys signed a block in which the order’s recipient received the order’s amount.

  1. Open the claim transaction on Sepolia. Read the imported block number and hash from its Imported event.
  2. Fetch that block’s BEEF justification from V3 with chain_getBlock, recompute keccak256(SCALE(commitment)) and recover both signers. Compare them with the keys below.
  3. Resend the same claim with one recipient byte changed. It reverts with SlotMismatch.

Encoding

Official docs still describe V1, so here is what V3 does, each line checked against live data.

MMR leaf
keccak256(u32le(parent_number) ++ parent_hash). The leaf added in block B commits to block B−1, and the leaf count at block n is n.
MMR append and bag
A node is keccak256(left ++ right), merging while the last peak’s height equals the current height. Bag from the rightmost peak: acc = keccak256(acc ++ peak).
Header
blake2b-256(SCALE(header)) is the block hash. Layout: parent_hash[32] ++ compact(number) ++ state_root[32] ++ extrinsics_root[32] ++ digest.
Revive storage
Revive.AccountInfoOf(address) holds the trie id. The child root sits under ":child_storage:default:" ++ trie_id; a 32-byte slot sits under blake2_256(slot), stored as 0x80 ++ word.
FillBook slot
fillKey = keccak256(abi.encode(orderKey, recipient, amount)); the slot is keccak256(abi.encode(fillKey, 0)); the word is payee | timestamp << 160.
Order key
keccak256(abi.encode(11155111, escrow, orderId)), so another chain or another escrow produces another key.

Prover CLI

Anyone can run these against public RPCs. A relayer can delay a claim with them; it cannot forge one.

talyx find-justified --after <block>     # next block with a stored BEEF justification
talyx build-import <B>                    # justification, peaks at B-1, SCALE header B-1
talyx build-claim <orderId> --at <B-1>   # main-trie and child-trie proofs of the fill
talyx verify <orderId>                    # every on-chain check, off-chain first
talyx import <B>                          # BeefyStateRoots.importBlock on Sepolia
talyx claim <orderId>                     # TalyxEscrow.claim, pays the recorded payee
talyx refund <orderId>                    # after the deadline plus 30 minutes
talyx fill                                # watch OrderCreated and fill on V3

The fill block must be at most B−1. The CLI scans for justifications rather than assuming their cadence, which shifts over time.
